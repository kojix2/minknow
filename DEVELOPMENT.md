# Development

Generated files:
- MinKNOW protobuf/gRPC outputs are kept under `src/generated`.

Code generation:

```sh
git submodule update --init minknow_api
make setup
make gen
```

Install `protoc` alongside Crystal and libnghttp2. The repository's `shard.lock`
pins the generator versions for development and CI; it does not constrain
applications that depend on this shard. `make gen-tools` rebuilds both plugins
from their current sources so changes in their required files take effect.

When adopting generator changes, update both dependencies together and commit
the lock and regenerated sources as one migration:

```sh
shards update grpc proto --without-development
make gen
crystal spec
crystal spec spec/live_reads_large.cr
```

Keep `shard.lock` in version control and use `shards install --frozen` for
ordinary development and CI. Applications that depend on this shard resolve
their own locks and need to update `minknow`, `grpc` and `proto` together when
adopting these generated APIs. Publish dependency commits before pushing a lock
that references them. The lock pins generators; the API schema remains pinned
by the `minknow_api` submodule.

`make gen` and `make gen-one` also regenerate the Google protobuf types used by
the API. Their schemas are pinned under `vendor/google/protobuf` instead of
depending on the host's protobuf include files. See `vendor/README.md` for their
version and license. To regenerate just those types, use `make gen-well-known`.
The checked-in output includes real descriptor messages, not a placeholder.

Run `crystal spec` to check the public wrapper and generated well-known types,
including FloatValue/DoubleValue without Float extensions, positive and negative
zero, non-finite values, unknown fields and truncated payloads. A known field
number with a different wire type is preserved as an unknown field, matching
the official Protobuf runtime. CI regenerates
all files and checks for differences before running specs and compiling examples.

Wrapper regression tests use a recording channel without a running MinKNOW
instance. They cover RPC request types, contexts, streaming, live-read setup and
actions, required calibration ranges and protocol run IDs, fractional timeouts,
and local authentication precedence, token files and manager-port lookup.
`make gen` also regenerates the Google RPC status type required by the v2 API
from its pinned schema under `vendor/google/rpc`.

`spec/live_reads_integration_spec.cr` also exercises the actual generated
`get_live_reads` client over local HTTP/2. It interleaves setup, a 128 KiB signal
response and action acknowledgements, preserves successful and failed server
completion, and reopens a stream after cancellation. The peer is a local test
service; it does not connect to MinKNOW or operate sequencing hardware.

CI shuffles examples with `github.run_id` as the reproducible seed. Replay a
failure with `crystal spec --order SEED`. The gRPC repository additionally tests
its candidate source and proto dependency against this consumer's current
default branch and its pinned schema, using explicit dependency overrides.

## Release Checklist

Before tagging a release:

- run `crystal spec`
- run `crystal run examples/manager_info.cr`
- run `crystal run examples/list_devices.cr`
- confirm CI passes on the default branch
- confirm generated files under `src/generated` are in sync with the tracked MinKNOW API inputs
